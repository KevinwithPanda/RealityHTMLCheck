THE LAST MILE · VERIFIED LIVE

A successful upload is not proof that users received the verified package.

Hosts can expose the wrong base path, miss case-sensitive assets, serve an older deployment, redirect outside the project, or transform bytes. verify-deploy contacts only the declared same-origin base path, retains no response body, Cookie, credential, or raw header, and returns LIVE MATCH, TRANSFORMED · REVIEW, BROKEN, or UNVERIFIED. A green receipt requires HTTPS, complete byte coverage, and all three live Chromium scenarios.

ONE REVIEWABLE WORKFLOW · VERIFY → DEPLOY → VERIFY

Deploy only materialized verified bytes, then check the public URL.

The reusable Pages workflow keeps RealityCheck in a contents-read verification job. Only a separate deployment job receives Pages/OIDC permission; after GitHub returns the URL, a third read-only job downloads the exact evidence run and creates the live receipt. It refuses pull requests, never manages domains or signs into a host, and never pretends a failed live check rolled anything back. CI stores the complete publish/live evidence—including two provenance-labelled diagnostic screenshots—in GitHub Artifacts; an UNVERIFIED run may label a screenshot capture scenario as having used verified-capsule fallback bytes.
